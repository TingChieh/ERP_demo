# AI 助手未付款客户查询 — 设计说明

**日期：** 2026-09-23
**状态：** 用户已确认
**范围：** 修复 AI 助手的未付款客户只读查询，并补齐查询结果展示

## 目标

让用户可以通过“现在还有哪些客户没付款”“哪些客户未收款”“xx 科技还欠多少钱”等自然语言，在 AI 助手中查询真实的未收应收账款，并直接看到客户、销售订单、金额和产生时间。

查询只读，不执行收款、付款或其他业务写入。明确要求确认收款、执行付款、支付或结算时，AI 助手仍返回安全提示，引导用户进入现有应收账款页面操作。

## 当前问题

`agent/service.py` 在调用 LLM 前检查高风险关键词。查询句“现在还有哪些客户没付款”包含“付款”，会被当成付款操作并提前返回错误，导致既有的 `get_unpaid_receivables` 工具无法执行。

即使查询工具执行成功，`agent/tools.py` 已经返回 `data.items` 明细，但 `static/js/assistant.js` 对普通消息只渲染 `content` 或 `message`，用户只能看到笔数和合计，无法看到具体客户。

## 非目标

- 不新增 AI 收款或付款能力。
- 不改变现有 `/receivables` 的收款流程和数据库状态转换。
- 不新增部分收款、多次收款、对账、发票或账龄分析。
- 不让模型直接生成 SQL、金额或客户实体。
- 不改变采购、销售、库存和补货工具的业务规则。

## 方案

采用“只读查询意图优先 + 明确写操作继续拦截”的方案，保留现有 LLM Function Calling 和后端工具作为真实数据边界。

### 意图判定

在 `AgentService.handle_message` 中增加只读未收款查询判定：

1. 识别包含查询/状态表达的消息，例如“哪些”“谁”“查询”“查一下”“还有”“没付款”“未付款”“未收款”“欠款”“应收”。
2. 若消息表达的是未收款查询，则不因“付款”或“支付”这些状态词触发高风险拦截，继续交给 LLM 选择 `get_unpaid_receivables`。
3. 对“确认收款”“执行收款”“立即收款”“确认付款”“执行付款”“支付给某客户”“结算”等明确动作表达，仍在模型调用前返回现有安全错误，不调用任何 ERP 工具。
4. 对其他高风险履约请求（入库、出库、发货）维持现有拒绝行为。

意图识别只负责安全边界，不解析客户名称、不计算金额，也不替代 `get_unpaid_receivables` 的数据库查询。指定客户的实体解析仍由现有 `_resolve_named(Customer, ...)` 完成。

### 后端查询响应

保留 `get_unpaid_receivables` 的查询和汇总逻辑，并扩充每条明细的展示所需字段：

- `receivable_id`
- `sales_order_id`
- `sales_order_no`
- `customer`
- `amount`
- `created_at`

查询结果仍返回后端计算的 `total_amount` 和 `items`，并带 `query_type="unpaid_receivables"` 供前端识别。每条明细包含 `receivable_id`、`sales_order_id`、`sales_order_no`、`customer`、`amount` 和 `created_at`。有结果时，`content` 也生成包含客户和金额的简洁中文摘要，确保 API 调用方即使不渲染结构化数据也能得到“哪些客户”的答案；无结果时继续返回明确的“目前没有未收应收账款”。

### 前端展示

`static/js/assistant.js` 对普通 `message` 响应保持安全的 `textContent` 渲染，并在存在 `data.items` 时追加未收应收明细卡片：

- 每行显示客户、销售订单号、金额和产生时间。
- 销售订单号链接到现有销售订单详情页。
- 卡片提供“查看应收账款”链接，用户可以进入现有 `/receivables` 页面确认收款。
- 数值和文本均来自结构化响应，通过 DOM `textContent` 写入，不使用 `innerHTML` 拼接数据库内容。
- 空列表不显示空明细卡片，只显示后端返回的无欠款提示。

助手欢迎文案和示例继续保留未付款查询入口，并将能力描述明确为“查询未收应收”，避免暗示可以直接收款。

## 数据流

```text
用户输入“现在还有哪些客户没付款”
  -> AgentService 识别为只读未收款查询，跳过状态词误拦截
  -> LLM Function Calling 选择 get_unpaid_receivables
  -> agent.tools 查询 status = "unpaid" 的 AccountReceivable
  -> 后端计算明细和 Decimal 合计
  -> API 返回 content + data.items
  -> 前端渲染客户/订单/金额，并提供应收账款入口
```

```text
用户输入“确认收款”或“执行付款”
  -> AgentService 识别为明确写操作
  -> 返回安全错误
  -> 不调用 LLM，不访问 ERP 写工具，不改变数据库
```

## 错误处理与安全约束

- 未付款查询没有数据时返回成功的只读消息，不视为错误。
- 指定客户不存在或名称有歧义时继续返回现有 clarification，并不查询或写入数据。
- LLM 返回未知工具、格式错误或异常时沿用现有安全错误响应。
- 所有付款/收款动作请求在模型调用前被拒绝；现有高风险测试必须继续通过。
- 前端无法识别结构化明细时仍显示普通 `content`，不阻塞查询结果。
- 查询和展示改动不能创建订单、应收/应付记录、库存流水，也不能修改任何财务状态。

## 测试策略与验收标准

新增或强化以下测试：

1. “现在还有哪些客户没付款”不会触发高风险拦截，并调用未收应收查询工具。
2. 查询结果包含客户名称、销售订单号、金额、产生时间和汇总金额。
3. 指定客户查询只返回该客户的未付款记录。
4. 没有未付款记录时返回明确的无欠款消息和空明细。
5. “确认收款”“执行付款”“支付给客户”等明确动作仍返回不支持提示，且不调用 LLM 或写入数据库。
6. 助手页面仍能渲染普通消息，结构化明细展示逻辑不会依赖 `innerHTML`。
7. 完整现有测试套件保持通过。

## 计划修改文件

修改：

- `agent/service.py`：区分只读未付款查询与明确付款/收款动作。
- `agent/tools.py`：补充应收明细字段，并生成包含客户明细的安全摘要。
- `static/js/assistant.js`：渲染未收应收明细和业务页面入口。
- `templates/assistant.html`：调整能力说明文案（如有必要）。
- `tests/test_agent_routes.py`：补充自然语言路由和高风险拒绝回归测试。
- `tests/test_agent_tools.py`：补充查询明细字段、空结果和客户过滤测试。

不修改数据库模型，不新增依赖，不改变现有结算路由。

## 设计自检

- 只读查询与写操作的边界明确，现有付款/收款安全规则不放宽。
- 金额和客户数据均来自数据库工具，模型不被信任为事实来源。
- API 文本响应和结构化响应都能独立回答查询，前端渲染失败不会丢失摘要。
- 前后端文件职责保持清晰：服务层判定安全边界，工具层查询数据，前端层展示数据。
- 范围限于一个可独立测试的功能修复，没有引入账龄、部分收款等无关需求。
